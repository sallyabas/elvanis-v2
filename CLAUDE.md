## What this is
A goal-driven AI execution audit platform for founder-led B2B SaaS / tech-enabled SMEs (20–200 employees). Client picks a business goal, submits evidence (native tool exports or fill-in templates — no live integrations in V1), and the system runs five parallel AI-drafted lenses, which a human reviewer must approve before a client ever sees them. Output is a financially-quantified top-3-priorities + 30/60/90 roadmap, with an AI Opportunity section gated by a readiness check.

**Relaunch decision:** this ships under the existing Elvanis brand/domain (`app.elvanis.com`), not a separate company — but on genuinely fresh infrastructure (new GitHub repo, new Supabase project, new Vercel project). The old Elvanis app/DB is untouched, kept as reference/rollback, never shared or reused. Deploy on Vercel's free URL during build/pilot; DNS cutover to `app.elvanis.com` is the last step, done only after `RESEND_FROM_EMAIL` is verified working on the new project.

Market sequencing: UK → Netherlands/Europe → Gulf (gated on UK/NL proof).

## Non-negotiable architecture principles
- **No hardcoded provider calls.** Every LLM call goes through the internal `ai-client` abstraction (see `lib/ai-client/`) so switching model/provider is a config change, not a multi-file rewrite. Elvanis was already forced through one painful Groq migration — don't repeat that.
- **Mandatory human review gate.** A `reports` row can never reach `sent` status without passing `pending_review` → reviewer `approved`. This is enforced at the DB/workflow level, not just a UI convention. Every finding is `draft` → `reviewer_edited` (optional) → `approved` before it can appear client-facing.
- **Isolated infrastructure.** New Supabase project, new env vars, new domain path. Never touch the old Elvanis DB/repo/tables.
- **Evidence-in, structured-out, per lens.** Each of the five lenses is an independent AI call with its own strict output schema — one lens failing must not block the others.
- **Business profile is a living record.** Every lens prompt reads the *current* profile/goal/evidence state at generation time, never a cached copy from signup. Changes are tracked in `company_profile_history`.
- **Source-agnostic evidence intake.** No OAuth/live integrations in V1. Per-lens native export upload (CSV/PDF) or fill-in template, reconciled via a merge-and-complete step. A known-source template library (Xero, QuickBooks, HubSpot, Salesforce, Jira, Intercom, Zendesk) auto-maps recognized files; unrecognized files fall back to generic parsing.

## Generic module review architecture (confirmed 2026-08-02)
AI Reliability Audit, Tender Readiness, and Data Protection Compliance all hit the same question: how do their findings get reviewed? Solved generically once here, not as a one-off for AI Reliability with the other two repeating the question right behind it — same principle already used for AI & Governance not being forced into the shared `LensModule` interface: **reuse the review mechanism, don't force the findings shape.**

**Schema** (`supabase/migrations/20260802140000_generic_module_review.sql`) — replaces the three separate `*_requests` tables (`tender_readiness_requests`, `ai_reliability_requests`, `data_protection_requests`), all three still completely empty and unreferenced by any code (a v0 scaffold predating the lens architecture's findings-structure lessons), so dropping and replacing needed no backfill:
- **`module_requests`** — plays the same role `reports` plays for the core audit: the review-gate container, reusing the exact same `report_status` enum (draft/pending_review/approved/sent) and the exact same "sent requires a reviewer" DB check constraint. `intake_data` (jsonb) holds whatever raw intake shape that module needs — genuinely module-specific, doesn't generalize (AI Reliability's is `{systemType, conversationalTranscripts, agentAutomationEvidence}`; Tender Readiness/Data Protection will have their own shapes).
- **`module_findings`** — plays the same role `lens_findings` plays, reusing the exact same `reviewer_status` enum (draft/edited/approved/rejected) and the same immutable-`ai_draft`-vs-`reviewer_edited_content` pattern. ## Multi-jurisdiction regulatory landscape
Full research and sourcing in spec §1.8c — read that before building any jurisdiction-aware logic in Tender Readiness, AI & Governance, or Data Protection Compliance. Summary: regulatory applicability is two independent signals, not one "country" field. ## `goalRelevance` hallucination — root-caused and fixed, 2026-08-05

The `directly_supports` fix (2026-08-01) closed one real gap but was never the full story — `generateValidatedJson`'s safety net kept catching the same class of failure (Execution/Product/Commercial on 2026-08-04, see immediately above), which meant the underlying cause was still live, just being caught cleanly instead of corrupting data. Investigated properly this time rather than accepting "the safety net catches it" as good enough, per explicit direction not to leave this as a known gap.

**Root cause, confirmed by reading all three failing lenses' own prompts, not guessed**: every one of Execution's, Product's, and Commercial's own `GOAL-RELEVANCE GUIDANCE` sections describes the `cash_flow_margin_efficiency` goal in identical terms — a real, material, often-quantifiable COST or DRAG on the goal ("labor-hours cost of decision latency," "whether low adoption... is wasting acquisition spend," "pricing pressure forcing discounting") that is nonetheless not the finding's *primary* obstruction of the goal. Neither existing negative value honestly fits: `directly_blocks` overstates it (nothing is actually preventing the goal), `indirectly_affects` understates it (the cost link is direct and traceable, not tangential). This is the same class of gap `directly_supports` fixed, just on the negative side rather than the positive one — a schema incompleteness, not a prompt-wording problem, exactly as the original fix's own docblock already correctly diagnosed for its own case.

**Reproduced live, not just reasoned about**: built evidence at exactly this semantic boundary (meeting-load cost under Execution, low-adoption-wasting-spend under Product, pricing-pressure-forcing-discounts under Commercial, all under `cash_flow_margin_efficiency`) and ran each several times. **Final, consolidated design (confirmed 2026-08-06, superseding two earlier scoping rounds in this same conversation)**: not a dev/Agile sprint — the paid implementation engagement itself, a bounded 2–4 week effort to fix ONE specific finding from an approved audit. Not an ongoing management relationship or embedded-CPO arrangement — a defined, time-boxed deliverable.
- **Entry point**: reviewer-triggered, from an approved report's selected finding. No in-app checkout — payment confirmed externally first, same pattern already used for Concierge/F2F Workshop.
- **Task creation**: AI-drafted from the selected finding, reviewer runs the same Accept/Edit/Reject mandatory-gate pass used everywhere else in this app — the sprint isn't client-visible until every task has a disposition.
- **Owner field**: simple free-text role label (Tester, Developer, PM, etc.), not a multi-user/permissions system.
- **Locked plan, once approved**: task description/owner/KPI target/due date are reference, not client-editable directly. A client wanting a change submits a note; it lands in the reviewer queue (reused infrastructure, not a new one) and the reviewer replies by email (existing Resend integration).
- **Status** (not started/in progress/done) is freely client-editable, no review needed — genuinely neutral reporting.
- **KPI actuals** are freely client-enterable, but a significant deviation from target (deterministic threshold check, never AI-judged) automatically surfaces to the reviewer queue via the same mechanism as the plan-change notes, different trigger — "a struggling KPI shouldn't go unnoticed until the end of the sprint." No separate AI-flagging engine, no dedicated audit-trail table — the note/queue item itself is the log.
- **Completion**: client signoff required, no auto-complete. A "gone quiet" reminder reuses the dormant `sprint_progress_checkin` job-type concept; never auto-closes. On signoff, the reviewer adds commentary — that commentary IS the final report, not a separately AI-generated document.
- **Explicitly out of scope**: sub-tasks/dependencies, multi-assignee, file attachments, comment threads beyond the plan-change notes, time-hours logging, drag-drop reordering, templates, in-app payment.
- **Three confirmed implementation details**: KPI-deviation replies send immediately, not on the next cron tick (the one deliberate exception to the "log now, dispatch on cron" pattern used everywhere else — a struggling implementation shouldn't wait up to 15 minutes for a reviewer response); KPI schema is `kpi_description` (text) + `kpi_target_value`/`kpi_actual_value` (numeric) + `kpi_direction` (`higher_is_better`/`lower_is_better`, set by the reviewer at task approval) rather than free text, so the deviation check can be genuinely deterministic; the deviation threshold is `app_settings`-backed, admin-adjustable, seeded at 20%, same pattern as every other benchmark in this build.

## Real auth bug found, root-caused, and fixed — /auth/callback's hardcoded reviewer-login fallback (confirmed 2026-08-07)

A real, reported bug: a first-time client using "Get started" received a confirmation email and, after clicking it, landed on `/reviewer-login` instead of client onboarding. Explicitly investigated by reproducing the exact flow before touching any code — not fixed blind.

**Root cause, confirmed by direct reproduction, not guessed**: [src/app/auth/callback/route.ts](src/app/auth/callback/route.ts) is shared by every auth flow (client and reviewer), and its failure-path fallback was hardcoded to `/reviewer-login` unconditionally — a leftover from when the reviewer flow was the only one that existed (the original comment literally said "reviewer login today"). This has nothing to do with client/reviewer auth "colliding"; it's one unconditional fallback that was never updated when the client flow was added on top.

**Why the exchange actually fails, confirmed by replicating the exact `signInWithOtp()` call this app makes**: this project uses `@supabase/ssr`'s default PKCE flow (no `flowType` override anywhere in the codebase, confirmed by grep) — `signInWithOtp()` sets a `code_verifier` cookie in the browser that requests the link, and redeeming the emailed `code` requires that same cookie still be present. This fails whenever the link is opened in a different browser/device than the one that submitted the form (checking email on your phone after submitting from your laptop, for instance) or visited first by an email provider's link-prescanning bot (the same class of failure this codebase already knew about for the reviewer flow, but had only ever worked around with the OTP-code fallback, never fully root-caused). ## Cron scheduling moved off Vercel's built-in cron, staying on Hobby tier (confirmed 2026-08-07)

Real cost decision, founder-researched and confirmed before building: Vercel's Hobby (free) tier caps cron jobs at once/day — the `*/15 * * * *` schedule `vercel.json` had shipped with would have **failed at deploy time** on Hobby, not just run less precisely. Explicit decision: stay on Vercel's free tier until the first 10 clients, rather than upgrade to Pro just for cron frequency.

**Solution — an external free scheduler hitting the existing route, zero code changes** ([.github/workflows/cron-tick.yml](.github/workflows/cron-tick.yml)): `/api/cron/tick` already only checks a bearer token against `CRON_SECRET` and has no idea (or need to know) whether Vercel or something else is calling it — confirmed by reading the route directly before building anything, exactly matching the ask. A GitHub Actions scheduled workflow (`*/20 * * * *`, using the repo's own free Actions minutes — negligible for a few-second curl call) now does the frequent check, calling the same route with `Authorization: Bearer ${{ secrets.CRON_SECRET }}`. [vercel.json](vercel.json) keeps its own once-daily cron (`0 3 * * *`, Hobby-compatible) pointed at the same route as a harmless backstop — if the GitHub Actions workflow ever silently stops firing, the worst case is exactly the once-daily cadence Hobby would have given standalone.

**Real caveats disclosed, not hidden**: GitHub Actions scheduled workflows are documented as "best effort" — a run can be delayed by several minutes during high platform load, occasionally more. Acceptable here since the one genuinely time-sensitive check (the 24h edit-window notification) tolerates a few minutes of slack. Also: GitHub auto-disables a scheduled workflow after 60 days with zero commits to the repo — not a concern for an actively-developed repo, but worth knowing if development ever goes quiet for two months during the pilot.

**Manual setup still needed (secrets were deliberately not handled by the agent — see the standing credential-handling rule)**: the repo needs two GitHub Actions configuration values set once, via `gh` CLI or the repo's Settings → Secrets and variables → Actions page:
- `CRON_SECRET` (secret) — same value already set as the `CRON_SECRET` Vercel project env var.
- `SITE_URL` (variable, not secret — it's just the deployed URL) — e.g. the live Vercel URL once deployed.

Via `gh` CLI: `gh secret set CRON_SECRET` (paste the value when prompted) and `gh variable set SITE_URL --body "https://<your-deployed-url>"`. Until both are set, the workflow will run on schedule but fail its curl call (visible as a red X in the repo's Actions tab) — a loud, visible failure, not a silent one.

## Working style
- Think like a CTO: scalability, dependencies, business impact — not just "does it run."
- Don't over-build ahead of proof. Exception: modules built from external research (Tender Readiness, AI Reliability, Data Protection) don't need a live client first — they're sequenced by engine-readiness, not by demand signal.
- Keep this file current. When real decisions get made or change in future sessions, update this file — don't let it go stale relative to the spec doc or actual code.
- **Never unilaterally drop, simplify, skip, or reduce the scope of a feature (confirmed 2026-08-03).** If something turns out harder than expected, ambiguous, or seemingly lower priority than other work, surface it clearly and ask — don't silently decide not to build it, and don't ship a reduced version without saying so. Reason: this session's own pattern showed real scope (the Saudi PDPL branch, the AI Reliability Audit design details, the regulatory-content-review gap) silently not happening simply because nobody re-raised it after the original document was written — the fix is flagging early, not assuming a checklist line will get picked back up on its own. This is a persistent rule, not a one-off — don't wait to be told again in a future session.
